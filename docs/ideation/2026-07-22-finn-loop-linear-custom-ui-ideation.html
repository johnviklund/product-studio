Evidence before direction

Grounding Context

Finn-loop is useful as a sharply stated operating model, but it is a brand-new repository created and hardened in four commits on July 22, 2026, with no releases. The lessons below therefore come from its mechanics, not from demonstrated production outcomes.

Finn-loop's actual system

Linear holds an editable issue contract and queue. GitHub holds pull requests and required checks. Three Claude Code skills specify, build, and review. Labels gate approval, repair, and escalation; humans merge.

Its strongest invariants

One pass handles one unit. Repair is considered before new work. A claim and review SHA are rechecked before action. Ambiguity leaves the queue with one answerable question. Review-ready evidence never authorizes merge.

Product Studio is already stronger below the UI

Versioned goal contracts, exact expected-state validation, exclusive leases, idempotent run manifests, immutable hashed mission packages, provider neutrality, and rebuildable projections are already delivered or specified.

The market is absorbing generic agent UI

Linear now exposes custom workflows, MCP, webhooks, GitHub automation, delegation, Agent Sessions, plans, and visible runtime states. GitHub exposes multi-provider coding-agent sessions in issues and project views. A generic agent monitor is becoming commodity.

Recommendation

Continue the custom Product Studio UI, but keep it deliberately thin. Its justification is not that Kanban is hard to buy; it is that Product Studio owns versioned workflow contracts, cross-product attention, evidence-bound approvals, and portable agent handoffs. Use Linear later only as an optional mirror or collaboration adapter. If the product ever narrows to a one-repo spec → build → review queue, Finn-loop shows that Linear plus GitHub is enough.

1

Keep the thin cockpit; make Linear an optional mirror

Axis
Product surface and source of truth
Confidence
92%
Complexity
Medium
Description

Keep Product Studio's custom Inbox, Board, Needs You, and detail surfaces because they render controller-native gates, exact-result approval, durable run evidence, portable missions, and cross-project attention. Add Linear only when collaboration or notification value is demonstrated, as an outbound projection with deep links. Goal versions, leases, approvals, attempts, and evidence remain file-owned.

Basis

direct: PRODUCT.md defines Product Studio as a local-first, cross-product governed-outcome control plane—not a generic project manager—and makes providers and GitHub adapters. external: Linear and GitHub now supply generic planning and agent-session visibility.

Rationale

This gives the custom UI a defensible boundary: it exists to show why work can advance, what evidence binds to the decision, and what you need to do next. It does not compete with Linear on generic issue management or with provider apps on live session telemetry.

Downsides

A future mirror introduces mapping and drift risk. Do not build it before a real collaboration or notification need appears; inbound Linear edits should be proposals, not state transitions.

2

Add an LLM contract optimizer at human approval gates

Axis
Workflow optimization with LLMs
Confidence
90%
Complexity
Medium
Description

Before a human accepts a specification or plan, run an advisory LLM pass that proposes unresolved behavior forks, contradictions between acceptance criteria and non-goals, missing failure states, scope risks, and verification gaps. Suggestions never mutate the accepted contract; only the human's accepted changes create a new version.

Basis

external: Finn-spec's stopping test asks whether two engineers would ship the same observable behavior, and Finn-loop identifies spec quality as its bottleneck. direct: Product Studio already separates bounded agent reasoning from controller-owned state and human completion authority.

Rationale

This is the cleanest expression of your differentiation: use model reasoning where ambiguity and quality benefit from it, while versioning and human approval keep the result trustworthy.

Downsides

An optimizer can create ceremony by inventing low-value questions. Start advisory-only and evaluate accepted versus rejected findings on completed specs before making it a gate.

3

Encode a Finn invariants pack in the controller

Axis
Queue and concurrency mechanics
Confidence
89%
Complexity
Medium
Description

Make one pass/one unit, repair before new work, immediate post-claim state recheck, exact-revision review, explicit exit to human attention, no silent retry, and no agent completion durable controller policy for the bounded patch loop.

Basis

external: Finn-build and Finn-review encode these as skill rules and labels. direct: Product Studio already has the stronger primitives needed to enforce them—exclusive leases, expected-state checks, attempt identity, idempotent manifests, and ROADMAP 3.2.

Rationale

Finn-loop demonstrates which operational rules matter most. Product Studio can turn those conventions into recoverable state rather than relying on an open terminal, mutable labels, or a cooperative assignee lock.

Downsides

Repair-first ordering needs starvation bounds so a pathological item cannot monopolize the portfolio. Scheduling policy belongs in the controller, not as a hard-coded board sort.

4

Carry an executable AC/non-goal evidence ledger end to end

Axis
Review and evidence loop
Confidence
88%
Complexity
Medium
Description

Give acceptance criteria and non-goals stable identifiers that flow from the accepted spec into the mission, agent result, deterministic checks, reviewer findings, approval, and later evaluation proposal. Each verdict binds to the exact result or commit hash; changed output invalidates the verdict.

Basis

external: Finn-build requires one evidence line per AC and one preservation line per NG, while Finn-review tags findings to criteria and re-reviews changed SHAs. direct: Product Studio already stores criteria, review-ready conditions, mission hashes, and immutable run evidence.

Rationale

The ledger makes quality traceable across independent seats. It also produces structured material for future real-work evaluations without relying on a model's narrative summary.

Downsides

Stable ID and version semantics must be designed carefully when a contract is edited; IDs cannot silently point to different meaning across goal versions.

Accepted spec · AC/NG IDs→Mission contract→Result + checks→Independent review→Hash-bound approval
5

Separate workflow phase from agent-session state

Axis
Contract and approval model
Confidence
95%
Complexity
Low
Description

Keep Execute, Review, Ship, and other phases as durable outcome gates. Treat queued, working, awaiting input, error, and finished as ephemeral states of one attempt. They may appear in an attempt summary or linked provider session, but never become workflow columns or transition authority.

Basis

external: Linear Agent Sessions expose six runtime states and GitHub shows coding-agent session status in issue/project views. direct: Product Studio phases represent durable lifecycle outcomes and its design explicitly keeps blocked and attention states out of permanent columns.

Rationale

This distinction protects the domain model from whichever agent platform happens to be connected and prevents a live execution UI from swallowing the product workflow.

Downsides

The detail panel needs clear naming for both layers. Prefer “Workflow phase” and “Current attempt” over exposing provider-specific terms.

6

Build a reason-coded Needs You queue

Axis
Queue and concurrency mechanics
Confidence
87%
Complexity
Medium
Description

Every stopped item receives one durable attention reason and one answerable question. The UI groups items by a small taxonomy—product decision, scope conflict, missing or red verification, risk gate, budget exhausted, and external dependency—without adding more board columns.

Basis

external: Finn-loop removes blocked and human-review items from automated queues until a human resolves the exact cause. direct: Product Studio already has structured controller conflict reasons, planned attention handling, and a design rule that attention is a state/filter rather than a column.

Rationale

This turns agent failure into a calm founder workflow: answer a decision, approve a risk, repair a check, or wait on an external dependency. It is much more useful than a generic “agent failed” badge.

Downsides

Keep the taxonomy small. Low-level errors belong in evidence; the reason code should describe the human decision or operational category.

7

Run a read-only Linear shadow benchmark

Axis
Product surface and source of truth
Confidence
72%
Complexity
Low
Description

After the manual handoff, evidence history, and bounded patch loop are dogfoodable, mirror a small set of Product Studio items into Linear for 30 days. Record which founder decisions remain materially better in the custom cockpit. Do not accept inbound state changes during the experiment.

Basis

reasoned: Finn-loop is a credible minimal baseline for what Linear plus GitHub can already coordinate, while Product Studio's differentiation can only be judged once its evidence and attention surfaces exist.

Rationale

The benchmark turns “Do I really need a custom UI?” into a reversible product test. It can reveal that some surfaces should be deleted, retained, or exported without surrendering canonical state.

Downsides

Doing this now would interrupt ROADMAP 2.3. Define the test after the MVP loop is usable, and set success criteria before writing an adapter.
